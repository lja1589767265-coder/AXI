# AXI 学习文章 README 写作规范

## 1. 适用范围

本规范用于项目中 A1、A2、A3 等 AXI 学习章节的 README 编写。

文章主要面向 AXI 初学者，并计划整理后发布到微信公众号。每篇文章既要忠实覆盖对应 PDF 章节，也要做到结构清楚、语言通俗、图文结合。

每个章节直接保存为项目根目录下的单个 Markdown 文件，不为章节单独建立文件夹。文件命名格式为：

```text
ARM_IHI_0022H_AMBA_AXI_and_ACE_Protocol_Specification_章节编号.md
```

例如 A1 章节使用：

```text
ARM_IHI_0022H_AMBA_AXI_and_ACE_Protocol_Specification_A1.md
```

## 2. 核心要求

每篇 README 必须满足以下要求：

1. 覆盖所对应 PDF 章节的全部知识点，不遗漏正文、小节、重要说明和原图表达的含义。
2. 使用中文重新组织和解释内容，不逐句机械翻译原文。
3. 先建立整体认识，再介绍术语和细节，最后总结并自测。
4. 专业结论以 Arm 规范为准；教学类比必须明确是辅助理解，不能替代协议定义。
5. 正文不添加网页超链接、站内跳转链接或“点击这里”等依赖链接的表达。
6. 文章脱离 GitHub 页面后仍应完整可读，可以直接复制到微信公众号编辑器中整理。
7. 首次出现的英文缩写必须同时给出英文全称、中文含义和一句通俗解释。
8. 所有图、表、示例必须在正文中被解释，不能只放图而不说明读图方法。

## 3. 固定文章结构

每篇 README 按以下顺序编写。

### 3.1 标题

格式建议：

```text
A1：AXI 入门——先看懂一次读写，再理解系统架构
```

标题应同时包含章节编号、核心主题和读者能获得的认识，避免只写“A1 学习笔记”。

### 3.2 开篇说明

开篇使用简短的引用块，说明：

- 阅读对象。
- 对应的规范名称、章节和页码。
- 本文覆盖范围。
- 预计需要的前置知识。

示例：

```text
阅读对象：第一次学习 AXI、具备基本数字电路概念的读者。
依据：Arm IHI 0022H，Chapter A1，原文页码 A1-25～A1-30。
```

### 3.3 学习目标

使用 3～6 条可以检查的目标。目标要描述“读完后会做什么”，例如：

- 能画出 AXI 五个通道的方向。
- 能说明一笔读事务和一笔写事务分别经过哪些通道。
- 能区分 Transaction、Burst 和 Beat。

避免使用“了解 AXI”“熟悉协议”这类无法判断是否完成的目标。

### 3.4 正文

正文按照以下认知顺序组织：

1. 这个机制要解决什么问题。
2. 系统中有哪些角色。
3. 一次实际操作怎样发生。
4. 协议对信号或行为作了什么规定。
5. 这样设计带来什么作用。
6. 初学者容易在哪里理解错误。

原 PDF 的章节顺序如果不利于初学者理解，可以调整讲解顺序，但不能遗漏知识点。文末必须提供原文覆盖对照表。

以一个问题引入概念时，问题导入部分建议控制在 500～700 字，只保留形成结论所需的背景、例子和边界。图片内部已经表达的信息，正文不再逐项重复；正文负责指出读图重点并解释结论。

### 3.5 易错点

每篇文章设置单独的易错点内容。每个易错点应包含：

- 常见错误理解。
- 正确结论。
- 为什么容易误解。
- 应到规范哪个章节继续确认。

例如，讲解 AW、W、B 时必须提醒：功能介绍的先后顺序不代表 AW 必须先于 W 完成握手。

### 3.6 原文覆盖对照表

文章结尾必须列出对应 PDF 的覆盖情况：

| PDF 章节或页码 | 原文知识点 | 本文位置 |
| --- | --- | --- |
| A1.1 / A1-26 | AXI 的设计目标与关键特性 | 第 1 节、第 6 节 |

这张表用于检查内容是否完整，不作为正文知识讲解的替代品。

### 3.7 自测题

每篇文章提供 5～10 道题，优先考查理解和应用，不只考查术语记忆。

答案放在题目之后，并与题目明显分隔。微信公众号编辑器不一定保留 HTML 折叠效果，因此发布时使用“参考答案”小标题直接展示答案。

### 3.8 下一章衔接

结尾说明下一章解决什么问题，以及读者在进入下一章前应掌握什么。只写章节名称和学习关系，不添加跳转链接。

## 4. 语言规范

### 4.1 通俗但准确

专业定义之后可以使用生活类比，但必须及时回到协议含义。

推荐写法：

```text
带宽可以类比为道路每秒能够通过多少辆车，延迟则像一辆车从出发到到达所需的时间。这个类比只帮助区分两个指标，AXI 中实际传输仍由时钟和握手信号决定。
```

避免把类比直接写成协议规则。

### 4.2 术语格式

术语第一次出现时使用以下格式：

```text
Outstanding（未完成事务）：请求已经发出，但对应事务还没有全部完成。
```

之后统一使用同一个中文或英文名称，不在“主机/主设备”“从机/从设备”等多种译法之间来回切换。

本项目默认使用：

| 英文 | 统一中文 |
| --- | --- |
| Master | 主设备 |
| Slave | 从设备 |
| Interconnect | 互连 |
| Transaction | 事务 |
| Burst | 突发传输 |
| Beat | 数据拍 |
| Register Slice | 寄存器切片 |
| Timing Closure | 时序收敛 |

如果引用新版规范中的 Manager、Subordinate 等术语，应说明它们与本文用语的对应关系。

### 4.3 句子和段落

- 一段只讲一个中心意思。
- 优先使用短句，避免连续堆叠多个从句。
- 一个小节开头先给结论，再解释原因和例子。
- 表格用于并列比较，不把大段正文强行塞入表格。
- 加粗只用于核心术语和关键结论，避免整段加粗。
- 信号名、数值、地址和代码使用行内代码格式。

### 4.4 结论强度

区分以下三种表达：

- “规范规定”：原文有明确要求。
- “通常”“可能”：取决于实现或系统环境。
- “为了理解，可以把它看成”：教学辅助解释。

不要把“支持某能力”写成“所有实现都会达到某性能”。

## 5. 配图规范

### 5.1 图片格式

微信公众号发布版本使用本地 PNG 或 JPG 图片，优先使用 PNG 绘制协议结构图和时序图。

- 不依赖 Mermaid 在线渲染。
- 不引用网络图片地址。
- 不直接截取受版权保护规范中的整页或大幅原图。
- 根据规范含义重新绘制教学图，并在图注中写明“教学重绘”。
- 图片统一放在项目根目录的公共 `images` 目录中。

图片统一存放在项目根目录的公共 `images` 文件夹，并按章节编号添加文件名前缀。不要为章节单独建立文件夹。

目录示例：

```text
ARM_IHI_0022H_AMBA_AXI_and_ACE_Protocol_Specification_A1.md
images/
├── a1-axi-five-channels.png
├── a1-write-transaction.png
└── a1-interconnect-topology.png
```

### 5.2 图片尺寸与视觉样式

- 建议按微信公众号正文宽度设计，导出宽度使用 1080 像素。
- 文字在手机屏幕上必须清晰，正文字号不小于 32 像素。
- 同一项目使用统一颜色：主设备用蓝色，从设备用绿色，互连用橙色，响应方向用紫色。
- 同一种通道在所有文章中保持相同颜色和名称。
- 背景优先使用白色，保证微信公众号浅色页面中的可读性。
- 图内只放必要信息，详细解释写在图下正文中。

### 5.3 图片命名和图注

文件名使用小写英文和连字符，例如：

```text
axi-five-channels.png
valid-ready-handshake.png
four-beat-burst.png
```

每张图下方提供图注：

```text
图 1：AXI 五个独立通道及信息流方向（教学重绘）
```

正文必须在图片出现前后说明：先看什么、箭头代表什么、不能从图中推导出什么。

### 5.4 推荐配图类型

一篇文章不追求图片数量，应优先绘制真正帮助理解的图：

- 角色关系图：主设备、互连、从设备之间的关系。
- 通道框图：五通道的方向和职责。
- 事务流程图：一次读写需要哪些通道。
- 时序图：VALID、READY 和数据在各周期中的关系。
- 层级图：Transaction、Burst、Beat 的包含关系。
- 对比图：正确理解与常见误解。

## 6. 表格与代码规范

表格列数尽量控制在 2～4 列，手机屏幕上不适合阅读过宽的表格。内容较长时改为分点说明。

代码、伪代码和信号组合必须放入代码块，并在代码块前说明阅读目的。代码块之后解释关键行，避免只贴代码。

时序示例必须明确：

- 时钟边沿。
- 信号由谁驱动。
- 哪个周期完成传输。
- 等待期间哪些信息需要保持稳定。

解释握手、流水线和等待行为时，优先提供逐周期时序图，而不是只用流程箭头。必须标明采样上升沿、有效传输、驱动方及省略信号的固定取值；按边沿前的信号值判断传输，图下逐拍解释。区分教学绘制与仿真采集，不将教学波形称为实测波形。比较协议时采用相同访问场景，明确实现能力假设，不能从示意延迟推导固定性能倍数。

## 7. 引用与版权规范

正文不添加可点击的外部链接。参考来源统一放在文章结尾，以纯文本方式书写：

```text
参考来源：Arm IHI 0022H《AMBA AXI and ACE Protocol Specification》，Chapter A1，A1-25～A1-30。
```

引用规范原句时只摘录解释所必需的短句，并同时提供中文解释。文章以自行组织的学习讲解为主，不大段复制或逐页翻译原文。

每篇文章结尾加入以下说明：

```text
本文为个人学习导读，不是 Arm 官方文档。协议设计与实现应以适用版本的官方规范为准。
```

## 8. 微信公众号发布前检查

发布前逐项检查：

- 标题能否说明本文主题和读者收获。
- 开篇是否写清规范章节、页码和阅读对象。
- 原文覆盖对照表是否包含所有小节和重要说明。
- 每个专业术语首次出现时是否已经解释。
- 图是否已转换为本地 PNG/JPG，并能在手机上看清。
- 图中的箭头、角色、信号方向是否准确。
- 是否删除了网页超链接、站内跳转和依赖 GitHub 的表述。
- 表格在手机屏幕上是否过宽。
- HTML 折叠、Mermaid、复杂 Markdown 是否已转换为公众号可用形式。
- 自测题是否能够检验理解，答案是否完整。
- 引用和版权说明是否存在。
- 是否通读全文，消除错别字、术语不统一和重复解释。

## 9. 完成标准

一篇章节 README 只有同时满足以下条件才算完成：

1. 对照 PDF 检查后，没有遗漏对应章节的知识点。
2. 初学者不打开其他页面也能理解文章主线。
3. 所有技术图都准确、清晰，并有正文解释。
4. 文章复制到微信公众号编辑器后，不依赖超链接、Mermaid 或 HTML 折叠才能阅读。
5. 专业结论、示例和自测答案经过复核。
6. 项目首页已经记录该章节及完成状态。
